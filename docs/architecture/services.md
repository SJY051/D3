| Boundary | Owns | Does not own | Initial caller or consumer |
|---|---|---|---|
| Identity | Accounts, login identities, refresh sessions, public profile | Rating, posts, matches | Gateway; community profile projection |
| Battle | Problems, queue decisions, rooms, outcomes, rating, RP, tiers | Source execution, login credentials, posts | Gateway; judge result events |
| Judge | Submission jobs, execution evidence, static/dynamic evaluation | Match winner, rating, public source | Battle job request; Judge0 |
| Community | Posts, follows, comments, likes, result/profile projections | Authoritative rating or identity | Gateway; Kafka events |

The API gateway uses the reactive Spring Cloud Gateway variant so HTTP and battle WebSocket traffic can share one ingress boundary. Domain services remain conventional Spring MVC applications unless their own requirements justify otherwise.

Gateway authentication does not replace service authorization. Every domain service validates the bearer credential at its own boundary and enforces ownership or role checks for the requested object; the judge boundary additionally rejects non-service callers.

## Communication rules

- Battle requests judge job acceptance synchronously through a versioned client boundary, then persists the returned stable submission ID with its match, player, attempt, `RUN`/`SUBMIT` mode and stable command ID before acknowledging acceptance. The job row is the sole accepted-submission correlation: only a positive-attempt `SUBMIT` may become accepted, and at most one accepted submit exists per match player. Distinct `RUN` commands receive distinct command IDs without incrementing the submission attempt; retries reuse the original ID.
- Judge publishes `submission.judged.v1` after durable evaluation.
- Battle publishes `match.finished.v1` and `rating.changed.v1` from an outbox after committing the result.
- Battle commits each player's named speed, dynamic-efficiency and submission-discipline score components plus the calculation/weight version atomically with the final total and result; later configuration changes never rewrite that historical explanation.
- Identity publishes `user-profile.changed.v1` for consumer-owned projections.
- Every consumer records `eventId` or an equivalent inbox key before applying an event.
- A projection may be stale, but it must retain the authoritative aggregate ID and version.

The browser opens `/ws/v1/battle/matches/{matchId}` with the two protocols `d3.battle.v2` and `d3.jwt.<access-token>`. The Gateway accepts one compact JWT protocol only on that exact UUID path, converts it to the bearer header before security, and removes the credential protocol before proxying so Battle can select only `d3.battle.v2`. Battle validates the user JWT again, allows one exact configured browser origin, and performs a PostgreSQL-backed participant lookup before upgrade. Each accepted session receives its own closed v2 projection. Per Battle instance, the registry has exactly one current session for each authenticated `(matchId, viewerId)`; a higher server-issued generation atomically replaces and normally closes the previous transport. The previous transport's late close, error, delivery failure, or command cannot evict, disconnect, or act as the replacement. After a match command transaction returns, its instance publishes only the match ID through an ephemeral Redis channel; every Battle instance re-reads the authoritative PostgreSQL projection and fans it out on a bounded executor to its local sessions. A shared coalescing publisher retains a failed match-ID fan-out and retries until Redis accepts it; per-match attempt generations prevent an older successful retry from clearing a newer failure, while local delivery and aggregate-version suppression make retries safe. Because successful Redis pub/sub cannot prove that every subscriber was connected, each instance also schedules a bounded periodic re-read for matches with local sessions. A transient PostgreSQL read or serialization failure defers that resynchronization without closing a healthy transport; a checked or unchecked `sendMessage` failure evicts the unusable transport and starts authoritative disconnect handling. This repairs missed notifications from PostgreSQL without replay storage or duplicate client events. A lazy local-session lookup keeps the retry publisher outside the WebSocket lifecycle dependency cycle. Aggregate version suppresses stale or duplicate sends, and a replacement session reads the latest authoritative snapshot instead of replaying partial client events. The closed Battle command v2 envelope activates only `READY` and `SURRENDER`: it requires a UUID match and idempotency key, derives the actor from the authenticated session, rejects client-owned fields, cross-match commands, duplicate JSON members, coercion and oversized frames, and commits through participant-bound receipts. A fresh command ID that produces no state change is rejected rather than stored. Battle maps an authenticated WebSocket open and close to a server-issued PostgreSQL generation, retries transient aggregate conflicts with the same generation, and ignores a late close from a superseded session. If the bounded inline close attempts all lose optimistic races, a coalescing in-process queue retains the highest failed generation per participant and retries it until PostgreSQL accepts it or authoritative state rejects it. Every mutating client command carries the registry-held generation into the same optimistic transaction and is rejected unless that generation is the actor's current connected generation in PostgreSQL. A current-generation close before match start clears readiness and returns the connection state to `CONNECTING`; the 30-second grace period begins only after `RUNNING`. A bounded scheduler captures server time and claims `RUNNING` matches whose match or reconnect deadline is due with PostgreSQL `FOR UPDATE SKIP LOCKED`. The domain applies whichever deadline occurred first, keeps the exact-time reconnect tie boundary deterministic, and commits each transition once. The service completes the bounded PostgreSQL batch before submitting match-ID fan-out to the bounded executor, so a Redis timeout cannot delay later deadline claims. Once the match deadline has selected `JUDGING`, an outstanding reconnect deadline may update connectivity on recovery but cannot replace the pending judged outcome. This makes lifecycle advancement autonomous and safe across Battle instances without moving durable truth into Redis. The generation stays out of the public snapshot and command contracts. ## Persistence rules

- Follow `docs/architecture/postgresql.md` for schema, indexing, transaction, pool, and migration rules.
- One local PostgreSQL cluster may host separate databases, but each service uses a separate role and credentials.
- Flyway migrations live with the service that owns the database.
- Cross-service database queries, foreign keys, and shared entity libraries are outside the contract.
- Redis values require a TTL and may be rebuilt or discarded without losing a committed result.
